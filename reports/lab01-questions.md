# Ответы на контрольные вопросы к лабораторной работе №1

## 1. Чем WSL2 отличается от WSL1? Почему для курса важен именно WSL2?

WSL1 транслировал системные вызовы Linux в вызовы Windows API — не было настоящего ядра Linux, поэтому многие Linux-инструменты работали некорректно (Docker, сеть, работа с файловой системой). WSL2 использует **настоящее ядро Linux**, запущенное в лёгкой виртуальной машине, что обеспечивает полную бинарную совместимость.

Для нашего курса важен именно WSL2, потому что Docker Engine и большинство DevOps-инструментов требуют настоящего ядра Linux и в WSL1 работать не будут.

## 2. Что хранится в `~/.ssh/id_ed25519` и в `~/.ssh/id_ed25519.pub`?

- `id_ed25519` — **приватный** ключ. Хранится только на моей машине, права `600`. Используется для доказательства владения ключом при подключении.
- `id_ed25519.pub` — **публичный** ключ. Его можно показывать и загружать в GitHub/GitLab.

Приватный ключ нельзя показывать, потому что любой, кто им завладеет, сможет выдать себя за владельца и получить доступ ко всем репозиториям и серверам, где зарегистрирован соответствующий публичный ключ.

## 3. Зачем нужна команда `ssh-agent`? Что произойдёт, если её не запускать?

`ssh-agent` — фоновый демон, который хранит расшифрованные приватные ключи в памяти. Позволяет ввести passphrase один раз при `ssh-add`, а затем не вводить её при каждой операции.

Если не запускать агент, при каждом `git push` или `ssh` будет запрашиваться passphrase (если она установлена). В учебной конфигурации passphrase пустая, поэтому разница незаметна, но в реальной работе агент обязателен.

## 4. В чём разница между `git config --global` и `git config --local`?

- `--global` — настройки для **всех** репозиториев пользователя, файл `~/.gitconfig`.
- `--local` — настройки **только для одного** репозитория, файл `.git/config` внутри него.

Локальные настройки **перекрывают** глобальные. Обычно локально задают другой email или имя — например, для рабочих проектов, отдельно от личных.

Есть ещё `--system` — для всех пользователей машины, используется редко.

## 5. Почему мы используем `docker compose` (через плагин), а не отдельный `docker-compose`?

- `docker-compose` (v1, с дефисом) — устаревший отдельный Python-скрипт, с 2023 официально deprecated.
- `docker compose` (v2, через пробел) — встроенный в Docker CLI плагин, написан на Go. Быстрее, поддерживается, работает с современными Compose-файлами.

v2 — современный стандарт, v1 больше не развивается.

## 6. Что означает флаг `--rm` в команде `docker run --rm hello-world`?

`--rm` — автоматически удалять контейнер после его остановки. Без флага контейнер останется в `docker ps -a` и будет копить мусор (занимать место, создавать лишние записи). Идеально для разовых команд и тестов.

## 7. Зачем мы добавляем пользователя в группу `docker`? Какие риски это несёт?

Чтобы иметь доступ к `/var/run/docker.sock` без `sudo` — иначе каждая команда `docker` требовала бы root. Добавление в группу даёт удобство.

**Риски:** доступ к Docker-сокету фактически эквивалентен root-доступу — можно смонтировать корневую ФС хоста внутрь контейнера и получить полный контроль над системой. Поэтому добавление пользователя в группу `docker` — это де-факто выдача прав sudo без пароля. Альтернатива — rootless Docker.

## 8. Что такое `IdentitiesOnly yes` в `~/.ssh/config` и зачем он нужен?

Указывает SSH использовать **только** тот ключ, который указан в `IdentityFile` для данного хоста, не перебирая остальные ключи из агента и `~/.ssh/`. Нужно, когда ключей много (личный, рабочий, для разных Git-хостингов) — предотвращает ошибку `Too many authentication failures` и гарантирует использование нужного ключа для конкретного сервера.
